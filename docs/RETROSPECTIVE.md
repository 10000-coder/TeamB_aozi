## 一、卡点清单

### A. 环境与链路（外部约束，只能绕，不能修）

| # | 现象 | 根因 | 解法 | 沉淀规则 |
|---|---|---|---|---|
| A1 | 本地容器 curl 目标站：TLS `Connection reset by peer` | 本机出网被白名单收敛（只放行 GitHub / PyPI / npm） | 用 Composio 远程沙盒（全出网 + node/npm/python）。沙盒可直连目标站、npm、pbs.twimg.com | **先做一次出网探针**再排计划；"能不能摸到目标"决定整条流水线的形状 |
| A2 | 本地无 GitHub 凭据 → `git push` 不可能 | 容器内没有凭证，也不该把 token 贴进聊天 | 在沙盒内用 `run_composio_tool()` 调 GitHub/Vercel 工具（Composio 凭据代理） | **凭据不该经过模型**。用工具侧的凭据代理，而不是要用户交码 |
| A3 | 19MB 二进制无法经逐文件 API 推送 | 本机→远端字节通道太窄 | 沙盒**自己**下载 84 个素材（清单里带原始 URL），只让 74KB 源码穿过模型 | **最小化穿越模型的字节**：能由远端自己取的，绝不自己搬 |
| A4 | 分片传输静默损坏：8000 字符实写 7998 | 模型转录不可靠（无报错） | 每片 md5 + 末端整体 sha256；不一致就重传 | **任何跨模型字节都要逐片校验**。"写成功了"不是证据，哈希才是 |
| A5 | Chromium 随机崩溃 | 磁盘 >95% 满，`/tmp` 堆满 PNG | 跑前清 `/tmp` | 渲染类任务把**磁盘余量**当资源来管 |

### B. 真值缺失（本项目最大的卡点，也是最大的一课）

| # | 现象 | 根因 | 解法 | 沉淀规则 |
|---|---|---|---|---|
| B1 | 第一轮"验收"打出 96.8% 并 APPROVED，实际作废 | 抓取方给的两张基准图是 1536×643 的伪图（不是 1440/375 全页），**验收对象根本不存在** | 亲手核基准尺寸，作废该轮结论 | **没有真值时，任何验收分数都是负价值**——它制造虚假置信 |
| B2 | 第一版做成了 Twitter 克隆，方向整体错误 | 靠"二手描述 + 合理猜测"建模，而不是读真实 DOM | 把抓取的 hydrated DOM 做成**可离线重渲染的副本**，基准自持、可随时重测 | **Gate 0：先冻结真值再动一行实现代码**。真值必须可离线重测 |
| B3 | 页高差 3–4 倍（4532 vs 13879） | 同上：形态就错了，不是细节不像 | 同上 | 尺寸/页高这类**不变量**是最便宜的"方向对不对"探针 |
| B4 | V-01"把 Launchpad 挪到右栏"把项目推得更远 | QA 的**猜测性合理化**被当成结论执行 | 回溯到原站 CSS，实为 3 列网格 gap 22px | **听起来合理的建议，没有原站证据不执行**；尤其"我觉得应该……"型建议 |
| B5 | 抓取方建议"暗色缺失头像回退默认头像"，采纳会破坏保真 | 它没查原站自带 `onerror="this.removeAttribute('src')"`（露出空板圆，非默认头像） | 核原站行为 → 我们已实现同一行为 → **不改** | 复核别人的建议时，去读**原站自己的 fallback 语义**；"更合理"≠"更忠实" |

## 二、可复用流程（下次直接照这个走）

```
Gate 0  冻结点 ──┐ 没有"可离线重测的真值"就不进入实现/验收
                 │ 验收标准必须写成一条**可执行命令**，禁止形容词
                 ▼
1 真值层   抓 hydrated DOM → 做成 offline-renderable 副本
           + 资产原始 URL 清单 + 每资产 sha256（离线基准必须图形齐全）
2 契约层   从真值**机械导出**（脚本），不手抄；保留 4 套布局/主题的并存渲染
3 实现层   手写只留给"必须渲染数据"的部分；其余由生成器 1:1 产出
           ★生成器必须确定性：干净沙箱重跑 → sha256 与原提交逐字节相同
4 测量层   几何 + 计算样式 + 像素 + 文本，双侧同视口/同 selector
5 盲区层   写明工具**不**检查什么
6 资产层   对**每个数据引用**做存在性审计（数据 → 文件），不止审计清单
7 传输层   xz+base64 → 8K 片 → 每片 md5 → 末端 sha256；远端能自己取的不搬
8 交付层   线上回抓全量资产重算 sha256；把产物哈希与"被验证过的构建"绑定
```

**额外得到的两条工程卫生**：
- 版本控制要用，但**别在有未提交改动时 `git reset --hard origin/main`**（本项目两次被它静默回滚）。
- 破坏性操作（force push / 删仓库 / 改历史）默认**停下问**，不做"顺手清理"。

## 三、多 agent 协作：实测收益分析

### 3.1 本项目每一次委派的净收益（事后逐条判定）

| 委派 | 产出 | 净收益 | 判定理由 |
|---|---|---|---|
| fetcher R1（抓素材/截图） | 1536×643 伪基准 | **负** | 直接导致 B1：在没有真值的情况下让验收流程继续跑 |
| fetcher R2（真抓取） | 2880×14400 / 750×28420 真基准 | **正（关键）** | 这是后面一切的地基；但它转述的"只缺 1 张""回退默认头像"都错 → **事实可用，结论要复核** |
| QA R1+R2（打分 86% → 96.8%） | 分数 | **负** | 无基准打分，且 V-01 建议把我们带偏 |
| QA R3（独立复跑） | 264 个真实差异像素 + 指出我的文本比对盲区 | **正（高价值）** | 此时**真值 + 工具都已存在** |
| QA R4（复跑） | 超时，无产出 | **负** | 与其它 bot 争同一台脆弱机器，静默失败 |
| dev（实现） | Twitter 克隆 + 6 项"精修" | **负** | 方向错误时，忠实执行 = **放大器**，执行越勤偏得越远 |
| 我自己（生成器 + 测量循环） | 核心价值全部在此 | **正** | 见 3.3 |

### 3.2 关键结构发现

**① 委派在方向错误时不是中性的，是放大器。**
dev bot 并不"做错了"，它把一份错误规格执行得很到位。**错误方向 × 强大执行力 = 比单干更快地偏离。**
所以判断"该不该派"之前，先判断"这一步的方向可信吗"。方向来自真值，真值没冻结前不该派活。

**② 独立复核的价值 = f(可复现工具 × 真值)。没有这两样，复核的价值为负。**
- QA R1/R2：两者皆无 → 产出一个**没人能反驳**的 96.8%，比没有 QA 更危险（虚假置信）。
- QA R3：两者皆有 → 一轮就抓出我漏掉的真缺陷。
**同一角色、两次结果相反，变量不是 agent 而是"基准与工具是否已就位"。**

**③ 信息每过一个 agent 就衰减一次。**
fetcher 的二手截图 → 我的二手描述 → dev 的实现，每跳都损失保真度。
本项目最有效的委派，接口都**窄到不需要理解真值**：抓一个 URL、跑一条命令、回传原始输出。
最无效的委派，接口宽到等于"按这个页面还原它"——那接口就是全部上下文，无法交接。

**④ 角色矩阵 ≠ 并行计划。**
一开始按 dev/qa/fetcher 建队，那是**组织隐喻**：它回答"谁负责什么"，
不回答"这一步能不能并行"。正确顺序是先画**任务依赖图**，标出哪些节点无共享可变状态，再决定 bot 数量。
本项目真实的依赖链几乎是纯串行的：真值 → 生成器 → 实现 → 测量 → 交付，
中间的"实现"根本无法与"测量"并行（测量对象就是实现产物）。

**⑤ 共享脆弱资源会让并行退化为互相干扰。**
多个 bot 争同一台机器的内存/磁盘/Chromium，失败模式还是**静默的**（`Connection error` / `timeout`），
看起来像"agent 不给力"，实际是资源竞争。

### 3.3 判据：什么时候该用多 agent

**必须委派（我做不到的事）**
- 需要另一条网络路径 / 凭据代理 / 另一台机器（本项目：出网、GitHub push、Vercel 部署）
- 需要**独立大脑**做对抗性复核，且**真值与可复现工具已就位**
- 真正可切分的体力活：N 个独立 URL / N 个独立文件 / N 次同构调用，接口窄、输出可校验

**不要委派（自己串行做更快更准）**
- 任务需要**单一心智模型**持续持有复杂真值（"从 DOM 反推整页并在 0.75px 内对齐"）
- 验收标准尚未冻结成命令（此时多一个 agent 只是多一个编造结论的源头）
- 子任务产出必须由"我理解真值"才能判断对错（此时委派=交付规格，而规格=全部上下文）
- 与测量/验证共享同一份可变产物（无法并行）

**一句话判据**：
> 只有当单元接口窄到"不需要理解真值"、且输出可机器校验时，委派才不损失保真度。
> 否则宁可不派。

### 3.4 下次的默认配置

- **默认 1 个执行者（我）**，串行推进 真值 → 生成器 → 实现 → 测量。
- 只在三种情况下开 bot：① 我摸不到的资源/凭据（如 fetcher 类）；② 真值与工具就位后的**对抗性复核**；
  ③ 已明确可切分且输出可哈希校验的批量作业。
- 验收 bot 的委派书**必须是"复现命令 + 回传原始输出行"**，明令禁止自评分——
  本项目已验证：一旦允许打分，就会得到 96.8% 这种无根据的数。
- 委派前先问三句：方向可信吗？验收能写成命令吗？失败了我会知道吗？

## 四、本项目仍然开口的事（不粉饰）

1. 线上 URL **没有**做浏览器端像素复测（沙盒无 Chromium）→ 线上验证是字节级 + 构建同一性。
2. 那 264 个差异像素的定性（原站是实图还是空板）未闭环；需在有出网 + 有 Chromium 的环境补拍 4 张卡。
3. 工具**不比对文本内容**，254/245 处空白符差异未处理（仅标注）。
4. `/t/<addr>` 页内数字是**抓取时刻的快照**，非实时数据（与 `coins.json` 同一取向）。
5. `main` 历史里仍有早期脚手架垃圾提交（文件树干净，仅历史不整洁）——是否删库重建待定。
